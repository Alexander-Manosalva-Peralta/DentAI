1. Resumen Ejecutivo y Fundamentos de Ingeniería

El presente informe técnico detalla la arquitectura completa de DentAI, una solución de ingeniería de software diseñada para operar en los consultorios de la Clínica Dental Docente de la Universidad Peruana Cayetano Heredia (UPCH). El sistema resuelve dos restricciones operativas severas: (1) la imposibilidad de tocar periféricos físicos durante el acto operatorio debido a la contaminación cruzada por bioaerosoles patógenos (Streptococcus mutans, Staphylococcus aureus, virus respiratorios), y (2) la rigidez arquitectónica del software clínico Smile (Cibermundo), el cual no cuenta con una API pública o servicios web accesibles para desarrolladores externos.

Para superar este desafío sin vulnerar la integridad de los sistemas institucionales, DentAI adopta una arquitectura Neuro-Simbólica implementada como una extensión web para Google Chrome (Manifest V3) respaldada por un Backend Gateway Institucional en la Intranet de la UPCH. En lugar de exponer credenciales de base de datos o exigir claves API en cada uno de los múltiples boxes de la clínica, el sistema centraliza la seguridad: la clave API de Google Gemini y las credenciales de la Base de Datos Central residen exclusivamente en el servidor central de la universidad, permitiendo que la extensión opere con cero configuración en cada puesto odontológico y sin salir a la tienda pública de Google.

2.1 Diagrama de Arquitectura de Alto Nivel y Modelo de Contenedores C4

Figura 1: Arquitectura de Alto Nivel y Modelo de Contenedores C4 de DentAI en Smile UPCH.

El Diagrama 1 descompone el sistema siguiendo el estándar C4 (Nivel de Contenedores y Componentes). Se identifican tres fronteras de aislamiento: (1) El entorno físico del Box Odontológico, donde el operador interactúa por voz frente a un micrófono direccional con cancelación pasiva; (2) El Runtime de la Extensión Chrome Manifest V3, compuesto por el SidePanelController (orquestador de interfaz y estados), el Motor Neuro-Simbólico (suite de guardias y enrutamiento léxico), el Background Worker (ciclo de vida y atajos) y el Content Script (inyector en el DOM de Smile); y (3) Los servicios externos institucionales, donde el Backend Gateway UPCH procesa la inferencia y las consultas seguras hacia la Base de Datos Central.

CRITERIOS DE INGENIERÍA Y ANÁLISIS TÉCNICO:
  • Aislamiento por Proceso: El Side Panel y el Content Script se ejecutan en contextos independientes comunicados por mensajes tipados.
  • Tolerancia al Ruido: La Web Audio API calcula el nivel RMS; si el ruido acústico de la turbina dental supera 75 dB sin modulación vocal armónica, el buffer se descarta preventivamente.
  • Inyección No Invasiva: Preserva intacta la sesión autenticada del odontólogo en Smile; no intercepta credenciales ni guarda contraseñas.

2.2 Arquitectura de Datos: Fase Actual (Mock Local) vs. Fase 2 Producción (Backend UPCH: Conexión BD + Zero-Config API Keys)

Figura 2: Arquitectura de Datos - Fase Actual (Mock Local) vs. Fase 2 Producción (Backend UPCH: Conexión BD + Zero-Config API Keys).

El Diagrama 2 aborda la solución de ingeniería diseñada específicamente para resolver los dos desafíos planteados por la DTI: (1) ¿Cómo se conecta la base de datos de la universidad sin comprometer la seguridad en una extensión cliente? y (2) ¿Cómo se gestionan las claves API en decenas de boxes sin exigir que cada alumno u odontólogo ingrese una clave personal ni exponerla públicamente?

1. FASE ACTUAL (Prototipo y Validación Local): La extensión opera con un catálogo sintético desidentificado en memoria volátil de cada box. Esto permitió validar la ergonomía, la cancelación de ruido y la inyección DOM sin interferir con la base de producción de la universidad.

2. FASE DE PRODUCCIÓN (Conexión Centralizada a BD UPCH y Zero-Config): Una extensión de navegador NUNCA debe conectarse directamente a un puerto SQL (Oracle/PostgreSQL) porque cualquier usuario podría inspeccionar el código y robar la contraseña de la base de datos de la universidad. La solución estándar de la industria consiste en implementar un 'DentAI Backend Gateway' (microservicio en Node.js o FastAPI) alojado en la Intranet de la UPCH:

  • La extensión en el box solo hace peticiones HTTPS internas al Gateway (ej: https://dentai-api.cayetano.edu.pe/pacientes?dni=...).
  • Solo el servidor Backend conoce la cadena de conexión y credenciales de la Base de Datos Central de la universidad, consultando de forma segura mediante un pool de conexiones controlado.
  • Solución al problema de la API Key: La Clave API Máster de Google Gemini reside ÚNICAMENTE en las variables de entorno del servidor Backend. Ninguna PC de ningún box almacena la clave API; los boxes operan con CERO CONFIGURACIÓN ('Zero-Config').
  • Despliegue Privado: La extensión no requiere publicarse en la Chrome Web Store pública; se distribuye en Modo Desarrollador Institucional cargado por red o como Extensión Privada de Google Workspace restringida al dominio @upch.pe.
CRITERIOS DE INGENIERÍA Y ANÁLISIS TÉCNICO:
  • Seguridad de Nivel Bancario: Las credenciales de la base de datos jamás tocan las computadoras de los boxes clínicos.
  • Blindaje de la Clave API: Cero riesgo de fuga, copiado o sobrecosto por alumnos; el servidor central de la universidad aplica cuotas y límites por box.
  • Despliegue Transparente: El odontólogo abre Chrome en cualquier box de la facultad y DentAI funciona inmediatamente sin pedir configuración técnica.

2.3 Diagrama de Secuencia UML: Ciclo de Vida End-to-End Voice-to-DOM

Figura 3: Diagrama de Secuencia UML - Ciclo Completo de Voz a DOM en Smile UPCH.

El Diagrama 3 ilustra la secuencia temporal cronológica de una interacción típica en el box. El ciclo abarca doce pasos coordinados: (1) El odontólogo emite el dictado clínico; (2) La Web Speech API captura el flujo fonético; (3) El Hero Orb pasa a estado LISTENING; (4) Se despacha la consulta al Backend Gateway; (5) Gemini retorna las entidades estructuradas; (6) El Motor Simbólico audita el DNI con regex de 8 dígitos, corrige fonemas elididos (ej. 'Lexander' a 'Alexander') y confina las variables a su contenedor; (7) Se construye la tarjeta de propuesta visual y el Hero Orb pasa a PROPOSAL_READY (anillo verde); (8) El operador dicta 'confirmar'; (9) El mensaje se transfiere al Content Script; (10) Se inyectan los valores y se disparan los eventos sintéticos en el DOM de Smile; (11) Se recibe la confirmación de inyección; y (12) El sintetizador de voz (TTS) emite la confirmación acústica.

CRITERIOS DE INGENIERÍA Y ANÁLISIS TÉCNICO:
  • Eventos Sintéticos de DOM: Se instancian eventos sintéticos con bubbles: true ('input', 'change', 'blur') para que los controladores internos de Smile registren la modificación de estado.
  • Confirmación en Dos Pasos: DentAI nunca escribe directamente de forma desatendida; requiere la confirmación explícita del operador profesional colegiado.

2.4 Diagrama de Flujo del Algoritmo de Decisión Neuro-Simbólica

Figura 4: Diagrama de Flujo del Algoritmo de Decisión Neuro-Simbólica.

El Diagrama 4 modela la lógica algorítmica bifurcada que gobierna el procesamiento de lenguaje. Ante cada buffer acústico, el sistema aplica un clasificador reactivo: si la entrada coincide con comandos deterministas de control ('ve a Preregistro', 'sube a Factura', 'buscar', 'confirmar', 'descartar'), la orden se enruta directamente al manipulador de pestañas y scroll del DOM sin consultar al LLM, reduciendo la latencia a menos de 15 milisegundos. Si se trata de un dictado clínico libre, la entrada se transfiere al Backend Gateway, cuyo resultado es canalizado obligatoriamente a través de la Suite de Guardias Simbólicas (validación de DNI, normalización de fonemas homófonos y barrera estricta entre secciones).

CRITERIOS DE INGENIERÍA Y ANÁLISIS TÉCNICO:
  • Aislamiento Estricto de Contenedores: Las guardias de frontera DOM impiden que los datos de facturación alteren la dirección domiciliaria del paciente.
  • Corrección Fonética de Nombres Propios: Normaliza omisiones acústicas (ej. elisión de la 'A' inicial produciendo 'Lexander' en lugar de 'Alexander') mediante análisis contextual de proximidad.

2.5 Diagrama de Clases y Módulos de la Extensión Chrome Manifest V3

Figura 5: Diagrama de Clases y Módulos de la Extensión Chrome Manifest V3.

El Diagrama 5 presenta el modelo de clases bajo el paradigma de programación orientada a objetos (POO). Se definen ocho módulos principales con alta cohesión y bajo acoplamiento: BackgroundServiceWorker (gestión de eventos de extensión y hotkey Alt+Shift+D), SidePanelController (controlador de vista y mediador de eventos), HeroOrbRenderer (motor de animación gráfica del orbe estilo Apple), AudioSpeechEngine (abstracción del reconocedor vocal Web Speech y cálculo RMS), GeminiInferenceClient (cliente REST resiliente con reintentos exponenciales), SymbolicGuardEngine (motor de reglas deterministas), DOMInjector (script de contenido con diccionarios de selectores) y la interfaz IPatientRepository con sus implementaciones para caché local y para el futuro Gateway institucional.

CRITERIOS DE INGENIERÍA Y ANÁLISIS TÉCNICO:
  • Patrón Mediator: El SidePanelController desacopla la captura de audio del inyector de DOM, garantizando tolerancia a fallos.
  • Patrón Command: Cada propuesta de llenado se empaqueta de forma transaccional con capacidad de descarte o rollback inmediato.

2.6 Diagrama de Máquina de Estados Finitos (FSM) del Hero Orb y Asistente

Figura 6: Diagrama de Máquina de Estados Finitos (FSM) del Asistente y Hero Orb.

El Diagrama 6 formaliza la Máquina de Estados Finitos (FSM) que controla el comportamiento del asistente y su representación visual. El sistema transita de manera determinista entre seis estados: IDLE (rostro robótico LED con respiración pasiva), LISTENING (transición animada a onda senoidal fluida sincronizada con la modulación acústica de la voz), THINKING (esfera cromática en rotación durante la inferencia y validación simbólica en < 350 ms), PROPOSAL_READY (anillo perimetral verde esmeralda con tarjeta de verificación en espera de confirmación), INJECTING (pulso expansivo de éxito e inserción en el DOM) y ERROR_GUARD (alerta luminosa ámbar/roja si falla la validación de un campo o si el ruido ambiental de la turbina satura el canal).

CRITERIOS DE INGENIERÍA Y ANÁLISIS TÉCNICO:
  • Experiencia de Usuario Médica Estilo Apple: Consciencia situacional periférica para que el odontólogo conozca el estado del asistente sin retirar la vista de la cavidad bucal del paciente.

  • Cero Contacto Físico (100% Manos Libres): Erradicación total de fómites hospitalarios sobre teclados y mouses durante la consulta.

3. Plan de Integración en Producción con la Base de Datos Central de la Universidad (UPCH)

Para responder a los requerimientos de la Dirección de Tecnologías de la Información (DTI) sobre cómo conectar la extensión a la base de datos de pacientes de la universidad y cómo desplegarla masivamente en los boxes, se establece la siguiente hoja de ruta técnica:

  • Fase 1 (Validación Funcional en Box): Operación con data sintética desidentificada y caché en memoria RAM. Permitió verificar tiempos de respuesta (<15 ms), filtrado de ruido de turbina (75 dB) y precisión del Hero Orb.
  • Fase 2 (Despliegue del Backend Gateway Institucional): DTI habilita un contenedor privado (Node.js/FastAPI) en el centro de datos o servidor de la universidad. Este Gateway es el ÚNICO punto que almacena la clave API máster de Gemini y las credenciales de la Base de Datos Central.
  • Fase 3 (Conexión Segura a la Base de Datos de la Clínica): El Gateway institucional se conecta mediante conexión segura interna (TCP seguro / pool de conexiones) a la base de datos oficial de la universidad (Oracle / PostgreSQL de Smile). Al dictar 'buscar paciente [DNI]' o 'mostrar pacientes registrados', la extensión consulta el Gateway y este retorna el JSON estructurado del paciente en milisegundos.
  • Fase 4 (Despliegue Masivo en Boxes sin Configuración): En lugar de configurar cada box manualmente, la extensión se distribuye como un paquete institucional administrado: los alumnos y docentes no necesitan ingresar claves API ni contraseñas de base de datos. La extensión se autentica automáticamente por la IP de la red del box o por la sesión activa de Smile.
  • Fase 5 (Distribución Privada - Sin Salir a Público): La extensión no se publica en la tienda general de Google Chrome. Se mantiene en Modo Desarrollador Institucional cargado por red local de la facultad, o se registra como extensión privada en la consola de Google Workspace de la UPCH accesible únicamente para cuentas corporativas @upch.pe.

4. Ciberseguridad, Protección de Datos Sensibles de Salud y Blindaje Informático para DTI UPCH

Ante la evaluación de la Dirección de Tecnologías de la Información (DTI) de la UPCH, el presente capítulo fundamenta rigurosamente cómo DentAI protege la confidencialidad de los pacientes y resuelve la seguridad de despliegue en múltiples boxes clínicos, dando cumplimiento a la Ley N° 29733 (Ley de Protección de Datos Personales del Perú) y directivas de MINSA.

PRINCIPIO DE BLINDAJE CLIENTE-SERVIDOR: DentAI adopta el principio de 'Thin Client' (Cliente Ligero): los boxes dentales NO almacenan claves API de IA ni credenciales de base de datos. Toda la lógica de conexión a la BD central y la clave máster de Gemini residen de forma segura en el Backend institucional de la UPCH, garantizando CERO PERSISTENCIA LOCAL en las computadoras de la clínica.

4.1 Ciclo de Vida y Almacenamiento de Datos: ¿Dónde se Aloja el DNI al Dictar?

Cuando el cirujano dentista o estudiante dicta la información del paciente en el box (ej. 'DNI 72736289, paciente Alexander Manosalva, calle Honorio Delgado 430'):

  • 1. Captura de Audio: El micrófono convierte la onda acústica en un buffer PCM efímero en la memoria RAM del navegador. El audio NUNCA se graba en ningún archivo ni disco local.
  • 2. Transcripción ASR: La Web Speech API convierte las muestras a texto dentro de la memoria volátil de la extensión (SidePanel).
  • 3. Consulta Centralizada al Backend: La extensión despacha el texto mediante llamada HTTPS cifrada (TLS 1.3) hacia el Backend Gateway de la UPCH. Dicho servidor contiene la clave API máster y consulta la Base de Datos Central institucional.
  • 4. Inyección en Smile y Purga de Memoria: Tras recibir la confirmación por voz ('confirmar'), los campos de Smile se llenan y la memoria RAM de la extensión se vacía inmediatamente (Garbage Collection de JavaScript). Ningún DNI ni historial se guarda en localStorage, cookies o IndexedDB de la máquina del box.

4.2 Resolución Técnica del Despliegue en Boxes y Gestión de Claves API

Un problema crítico en clínicas con decenas de boxes es la gestión de claves API y la distribución del software. DentAI lo resuelve mediante tres directrices de arquitectura:

  • 1. Cero Claves API en los Boxes (Zero-Config Client): Si cada alumno tuviese que ingresar una clave API, existiría riesgo de copiado, costos descontrolados o interrupción de servicio. Al residir la clave en el Gateway institucional, los boxes clínicos tienen 'Zero-Config': el alumno o docente abre Smile, activa DentAI y el sistema opera de inmediato sin solicitar claves técnicas.
  • 2. ¿Modo Desarrollador o Chrome Web Store Pública? Para proteger la propiedad intelectual de la universidad y evitar que la herramienta sea descargada por terceros fuera de la UPCH, existen dos modalidades aprobadas por DTI:
    • Modalidad A (Modo Desarrollador Institucional): La extensión se carga en modo descomprimido desde una carpeta compartida en la red interna de la clínica (ej. \\servidor-clinica\DentAI). No pasa por la tienda de Google ni sale a internet.
    • Modalidad B (Extensión Privada en Google Workspace UPCH): Se publica en la Chrome Web Store bajo visibilidad 'Privada para la Organización Universidad Peruana Cayetano Heredia'. Solo las cuentas institucionales (@upch.pe) pueden instalarla y se actualiza de forma automática en todos los boxes vía políticas corporativas de DTI.
